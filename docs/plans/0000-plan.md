## 1. Objective

Refactor the complete OAK implementation so that each concern has one clear owner, each package has one clear purpose, and future changes require editing the smallest possible set of files.

The refactor must preserve all existing OAK behaviour.

The completed repository must:

* keep the current OAK language unchanged;
* keep the current Pydantic models unchanged in meaning;
* keep the current public Python API;
* keep canonical OAK renders byte-identical;
* keep generated outputs byte-identical;
* keep example `.oak.md` files byte-identical;
* keep validation and execution error behaviour unchanged;
* remove duplicate semantic implementations;
* remove large mixed-responsibility modules;
* establish a clear dependency direction;
* use focused packages instead of broad monolithic files;
* retain explicit closed registries rather than dynamic registration;
* leave no obsolete files, paths, aliases, shims, or duplicate implementations.

This is one complete refactor. The phases below are implementation checkpoints, not versions, releases, or separately deliverable products.

## 2. Problem statement

The implementation works, but several files currently contain too many unrelated concerns.

### `oak/parse.py`

It currently owns:

* UTF-8 decoding;
* line-ending normalization;
* grouping inference;
* part splitting;
* XML-like attributes;
* Markdown attributes;
* entry grouping;
* constant parsing;
* JSON parsing;
* CSV parsing;
* YAML parsing;
* schema constraint parsing;
* `WHERE` parsing;
* process value parsing;
* condition parsing;
* binding suffix parsing;
* every process step parser;
* process parsing;
* trigger fact parsing;
* interface parsing;
* parse diagnostics;
* top-level document orchestration.

It also imports part order and built-in instructions from renderer modules. The parser and renderer should be sibling consumers of shared definitions, not dependencies of each other.

### `oak/node/graph.py`

It currently owns:

* entry iteration;
* entry indexing;
* duplicate detection;
* typed local target lookup;
* interface direction checks;
* value reference checks;
* static JSON value evaluation;
* condition evaluation;
* static branch analysis;

* process contract validation;
* call contract validation;
* process flow validation;
* process call-cycle detection;
* trigger validation;
* trigger overlap proofs;
* tool contract validation;
* whole-node validation.

This is one-document validation, not one cohesive graph component.

### `oak/node/parts/processes.py`

It currently owns:

* typed target aliases;
* process values;
* value bindings;
* condition models;
* process step models;
* process model;
* model-local validators;
* value and step traversal;
* process binding visibility analysis;
* act contract validation;
* call contract validation;
* process contract validation.

Model declarations, reusable semantics, and cross-entry validation should not share one file.

### `oak/node/parts/schemas.py`

It currently owns:

* all constraint models;
* datatype checking;
* examples;
* bound resolution;
* `Where`;
* authoring helpers;
* schema-binding diagnostics;
* schema binding;
* `Schema`;
* template and `WHERE` relationship validation.

The constraint language, schema model, and runtime binding engine are related, but they need separate modules.

### `oak/execute.py`

It currently owns:

* arrival models;
* emissions;
* execution results;
* execution errors;
* tool contracts;
* JSON comparison semantics;
* value resolution;
* condition evaluation;
* tool invocation;
* parallel work;
* schema validation;
* process invocation;
* every process step;
* interface activation;
* state preparation;
* trigger matching;
* public execution orchestration.

Execution state is passed through long argument chains rather than represented by explicit runtime context objects.

### `build/examples.py`

It currently owns almost all repository verification. It also imports private parser functions such as `_steps`, `_triggers`, `_schemas`, `_condition`, and `_value`. This makes build verification depend on parser implementation details rather than an intentional fragment-parsing interface.

The intended dependency direction is:

```text

    ↓
base and rules metadata
    ↓
node models and process/schema semantics
    ↓
node validation
    ↓
resolution
    ↓
execution

node models + surface descriptors
    ↓
parser and renderers

    ↓
```

* [ ] `oak.vocabulary` must not import `oak.node`.
* [ ] Node model modules must not import parsing.
* [ ] Node model modules must not import rendering.
* [ ] Node model modules must not import resolution.
* [ ] Node model modules must not import execution.
* [ ] Node validation must not import parsing.
* [ ] Node validation must not import rendering.
* [ ] Node validation must not import resolution.
* [ ] Node validation must not import execution.
* [ ] Parsing must not import an OAK renderer.
* [ ] OAK rendering must not import the parser.
* [ ] JSON-LD rendering must not import the parser.
* [ ] Resolution must not import execution.
* [ ] Execution must not import parser-private functions.
* [ ] Build checks must not import underscore-prefixed parser functions.
* [ ] Internal package modules must not import from the root `oak` barrel.
* [ ] Internal package modules must import the narrow owning module.
* [ ] Package `__init__.py` files must contain exports, not business logic.
* [ ] No circular imports may be hidden by broad barrel imports.

### Ownership rules

```text
node model modules
    fields, discriminated unions, defaults, metadata, model-local invariants

node validation
    relationships between entries in one document

resolution
    relationships between documents

execution
    one runtime cycle over a resolved graph

surface
    authored text descriptors

render
    model-to-text or model-to-JSON-LD conversion

parse
    text-to-model conversion

rules
    stable validation and authoring instruction records

build
    output generation and product verification
```

## 9. Shared semantic definitions

The current implementation duplicates strict JSON comparison and related operator handling. The refactor must create one definition of each semantic rule.

### Process operator module

`oak/node/parts/processes/operators.py` should own:

* `ConditionOperator`;
* canonical operator identifiers;
* authored operator phrases;
* reverse-operator mapping;
* inverse-operator mapping;
* strict JSON equality;
* ordered operand classification;
* pure comparison evaluation.

Example target interface:

```python
ConditionOperator = Literal[
    "equals",
    "not_equals",
    "less_than",
    "less_than_or_equal",
    "greater_than",
    "greater_than_or_equal",
]

OPERATOR_TEXT: Mapping[ConditionOperator, str]
OPERATOR_BY_TEXT: Mapping[str, ConditionOperator]

def json_equal(left: object, right: object) -> bool:
    ...

def ordered_pair(
    left: object,
    right: object,
) -> tuple[int | float | str, int | float | str] | None:
    ...

def compare_values(
    operator: ConditionOperator,
    left: object,
    right: object,
) -> bool:
    ...
```

* [ ] Validation uses these functions.
* [ ] Execution uses these functions.
* [ ] Parsing uses `OPERATOR_BY_TEXT`.
* [ ] Rendering uses `OPERATOR_TEXT`.
* [ ] Trigger overlap analysis uses the same reverse and inverse mappings.

## 10. Code quality requirements

### Module design

* [ ] Each module has one sentence in its module docstring stating its single responsibility.
* [ ] Each public function and public class has a useful docstring.
* [ ] Package `__init__.py` files contain explicit imports and explicit `__all__`.
* [ ] No package `__init__.py` performs validation, parsing, rendering, or execution.
* [ ] Closed model sets remain explicit discriminated unions.
* [ ] Closed registries remain explicit tuples.
* [ ] No runtime decorator registration is introduced.
* [ ] No automatic filesystem or module discovery is introduced.
* [ ] No generic utility module is introduced.
* [ ] A helper used by only one module stays in that module.
* [ ] A helper moves upward only when at least two owning modules require it.

### Functions

* [ ] Replace boolean mode flags with named entry points where they conceal different concepts.
* [ ] Replace repeated argument bundles with typed context objects.
* [ ] Do not pass parser state as five separate arguments.
* [ ] Do not pass executor state as eight or nine separate arguments.
* [ ] Prefer early returns over deep nesting.
* [ ] Prefer typed dispatch over long mixed-purpose functions.
* [ ] Use structural pattern matching only where it improves clarity.
* [ ] Preserve authored-order processing.
* [ ] Preserve deterministic diagnostic ordering.
* [ ] Do not catch broad exceptions unless translating one external boundary into an OAK error.
* [ ] Keep exception translation close to the boundary that owns the error type.

### Typing

* [ ] Use `TYPE_CHECKING`, not `if False`, for type-only imports.
* [ ] Keep Pydantic field types unchanged.
* [ ] Preserve strict adapters.
* [ ] Build each reusable `TypeAdapter` once.
* [ ] Use `Mapping` for read-only parameters.
* [ ] Use mutable collections only where mutation is part of ownership.
* [ ] Keep runtime context types explicit.
* [ ] Do not replace meaningful types with `Any`.
* [ ] Do not add casts merely to silence unclear ownership.
* [ ] Avoid stringly typed package-internal dispatch where an existing discriminated type is available.

### Formatting and naming

* [ ] Expand touched compressed one-line declarations into readable multi-line declarations.
* [ ] Keep exact domain names.
* [ ] Use names that state ownership and result.
* [ ] Avoid vague names such as `data`, `item`, `thing`, `handler`, or `value` where a more exact domain noun exists.
* [ ] Retain short conventional names where their scope is obvious.
* [ ] Remove comments that only repeat the code.
* [ ] Keep comments that explain a non-obvious invariant.
* [ ] Keep error messages readable and stable.
* [ ] Do not optimize for the fewest physical lines.
* [ ] Optimize for the fewest concepts a maintainer must hold at one time.

### Size guardrails

These are design checks, not reasons to create artificial files.

* [ ] `build/examples.py` is reduced to a small runner, preferably under 100 lines.
* [ ] No algorithmic production module exceeds 20 KB without a written justification in the final report.
* [ ] No module combines public models, cross-entry validation, parsing, and runtime execution.
* [ ] Declarative registries may exceed ordinary module size when splitting them further would reduce readability.
* [ ] Complete declarative examples may remain large when their single-document structure is clearer in one file.
